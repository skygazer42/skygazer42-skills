## 一句话定位

基于真实代码和行为路径审查前端变更，输出按严重度排序、可定位、可修复的问题。

## 适用场景

当请求的主要目标是“判断前端改动有没有问题”时使用，包括：

- 审查前端 Pull Request、提交或本地 diff。
- 检查交互、表单、导航和状态变化是否正确。
- 查找加载、空状态、错误、重复操作和取消流程中的回归。
- 检查语义结构、键盘、焦点、标签、通知和响应式风险。
- 检查不必要渲染、客户端包体、危险 HTML、前端密钥和信任边界。
- 判断测试是否覆盖高风险用户行为。

典型请求：

```text
审查这个结账表单改动，优先报告会影响用户或数据的阻塞问题，不要修改文件。
```

## 不适用场景

- 用户已经要求实现或修复：使用 `web.frontend-implementation`。
- 主要目标是启动应用、运行浏览器和复现问题：使用 `web.frontend-testing`。
- 主要审查 API、数据库或后端服务：使用 `backend.backend-review`。
- 只要求格式化、改名或统一代码风格：使用项目自己的 Lint/Formatter 更合适。

## 执行前需要的信息

- 变更说明和验收标准。
- diff、受影响组件、路由、数据客户端、样式和测试。
- 能够验证行为的相关实现，而不只是文件名或摘要。
- 如需运行验证，对应的项目命令和环境。

缺少 diff、实现或验收标准时，审查必须缩小到现有证据能支持的范围。

## 执行流程

1. 阅读变更说明、diff 和受影响代码。
2. 从用户输入一路追踪状态、请求和渲染结果。
3. 检查正常路径以及适用的加载、空、错误、校验、取消和重复交互路径。
4. 检查语义、键盘、焦点、标签、通知、对比度假设和响应式布局。
5. 检查渲染成本、包体积、危险 HTML、密钥和信任边界。
6. 判断测试是否覆盖真实风险，而不是只覆盖快照或实现细节。
7. 只输出有证据的问题，并按严重度排序。

## 交付结果

每条发现必须包括：

- 严重度和是否阻塞。
- 对用户、数据、安全或维护的具体影响。
- 文件、行号或可定位的受影响路径。
- 支持结论的代码或运行证据。
- 最小可行的修复方式。

如果没有发现问题，应明确写出“未发现可确认缺陷”，同时列出未执行的浏览器、设备、接口或部署验证。

## 权限

| 权限 | 声明 | 用途 |
| --- | :---: | --- |
| 网络 | 否 | 默认基于本地仓库证据审查 |
| 读文件 | 是 | 阅读 diff、实现、样式、配置和测试 |
| 写文件 | 否 | 审查模式默认不修复 |
| 执行命令 | 是 | 运行只读或验证性检查以确认发现 |

## 默认边界

- 不修改文件，除非用户另行明确要求修复。
- 不把审美、格式、命名或框架偏好当成缺陷。
- 实现可读时，不根据文件名或 diff 摘要猜运行行为。
- 没有操作浏览器时，不声称视觉或交互结果已经验证。
- 没有明确影响和证据的问题不进入正式 findings。

## 失败时如何处理

如果缺少 diff、相关实现或验收标准，列出缺失证据，只审查当前能够确认的路径。对尚未运行的浏览器或集成行为，以“残余风险”表达，不能冒充已确认缺陷。

## 行为案例

当前案例位于 [`tests/cases.yaml`](tests/cases.yaml)：

- `finds-interaction-regression`：必须识别请求未完成前重复提交造成的用户和数据影响。
- `separates-evidence-from-risk`：没有浏览器时必须区分已确认代码问题与未验证布局风险。

## 与相邻 Skill 的区别

```text
Frontend Review：        找出问题，默认不修改
Frontend Implementation：实现或修复前端功能
Frontend Testing：       用自动化或浏览器证明行为
```
