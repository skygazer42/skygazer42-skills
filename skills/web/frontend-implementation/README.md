## 一句话定位

在现有项目的技术栈和设计系统内，实现可访问、可响应并且能够验证的前端功能。

## 适用场景

当请求的主要目标是“修改前端产品行为”时使用，包括：

- 新增或修改页面、路由、组件和布局。
- 实现表单、校验、提交、错误提示和成功反馈。
- 修改交互状态、客户端状态管理或数据流。
- 把已有界面连接到现有 API。
- 修复响应式、键盘操作、焦点或语义结构问题。
- 在现有组件库和 Design Token 内完成 UI 功能。

典型请求：

```text
实现账户设置页，复用项目现有表单组件，并覆盖保存失败和字段校验状态。
```

## 不适用场景

- 只要求指出前端问题，不要求修改：使用 `web.frontend-review`。
- 只要求运行浏览器流程、复现问题或补测试：使用 `web.frontend-testing`。
- 主要修改 API、数据库、任务或服务：使用 `backend.backend-implementation`。
- 只需要一个脱离仓库的教学代码片段：普通问答通常更合适。

## 执行前需要的信息

Agent 会尽量从仓库中找到以下内容；缺失且会改变结果时才向用户确认：

- 用户目标、验收标准和明确不在范围内的内容。
- 相关路由、页面、组件、样式和状态管理方式。
- 现有设计系统、组件库、Token 和工具函数。
- API 契约、加载方式和错误格式。
- 项目的启动、类型检查、Lint、测试和构建命令。
- 已有测试以及需要支持的浏览器或视口。

## 执行流程

1. 阅读请求、验收标准和相关代码入口。
2. 追踪从用户操作、组件状态、网络请求到最终渲染的真实路径。
3. 优先复用已有组件、样式、工具和依赖。
4. 实现范围内最小而完整的改动。
5. 根据功能覆盖加载、空、错误、成功、禁用和校验状态。
6. 检查语义 HTML、键盘访问、可见焦点、标签、错误反馈和响应式行为。
7. 运行仓库现有的最小相关检查，并报告未能验证的部分。

## 交付结果

在有工作区时，默认交付真实仓库改动，而不是孤立代码片段。最终说明应包含：

- 实现了什么用户行为。
- 哪些验收标准已经满足。
- 修改了哪些文件。
- 运行了哪些命令和检查。
- 哪些结论来自自动化测试，哪些来自浏览器或视觉观察。
- 还有哪些环境相关内容未验证。

## 权限

| 权限 | 声明 | 用途 |
| --- | :---: | --- |
| 网络 | 否 | Skill 本身不要求访问外部网络 |
| 读文件 | 是 | 阅读项目代码、配置、样式和测试 |
| 写文件 | 是 | 实现页面、组件、样式和测试改动 |
| 执行命令 | 是 | 运行类型、Lint、测试、构建或本地应用命令 |

权限是仓库审核声明，实际执行仍受 Agent 平台和用户授权限制。

## 默认边界

- 不因为偏好替换项目框架、状态方案或设计系统。
- 标准平台能力或已安装依赖可以完成时，不新增依赖。
- 不覆盖无关用户修改，不加入生产 Mock 数据。
- 状态保持局部，除非确实需要跨组件共享。
- 不制造重复派生状态或无必要的 Effect。
- 没有实际检查时，不声称响应式、无障碍或视觉效果正确。

## 失败时如何处理

如果需求或仓库无法确定关键行为，只实现无歧义部分，并指出缺少的具体决策。如果命令不能运行，保留执行命令和失败证据，不把“代码已写”说成“功能已验证”。

## 行为案例

当前案例位于 [`tests/cases.yaml`](tests/cases.yaml)：

- `reuses-existing-system`：新增表单时必须复用现有组件和 Token，覆盖校验与错误状态。
- `refuses-unverified-claims`：没有浏览器时必须披露视觉和响应式验证缺口。

## 与相邻 Skill 的区别

```text
Frontend Implementation：修改产品代码并交付功能
Frontend Review：        默认只读，寻找证据充分的问题
Frontend Testing：       运行或补充验证，证明行为是否成立
```
