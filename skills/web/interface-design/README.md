# Interface Design（系统界面设计）

## 一句话定位

设计 dashboard、admin 后台、SaaS 应用、工具类产品的界面——追求信息清晰、一致可预测、高效可用，核心取向是「最少惊讶」。

## 适用场景

- 后台管理系统、admin panel。
- SaaS 应用主界面、数据看板 / dashboard。
- 内部工具、开发者工具、配置界面。
- 任何信息密集、以完成任务为目标的界面。

## 不适用场景

- 营销/创意网页、landing page、作品集、发布页——用 `web.frontend-design`（那要视觉冲击，这要高效可用，取向相反）。
- 把设计落地为代码——用 `web.frontend-implementation`。
- 复刻现有网站——用 `web.web-clone`。

## 执行前需要的信息

- 产品/系统的用途和主要用户任务。
- 涉及的数据类型（要展示什么表格/图表/指标）。
- 是否已有设计系统/组件库。

## 执行流程

1. 理清主要用户任务和信息架构。
2. 建立设计 token（间距尺度、语义色、字号阶梯）和组件模式。
3. 用信息密度与层级组织每屏，规划清晰的扫描路径。
4. 设计数据展示（表格/图表/指标）和完备状态（加载/空/错误/成功/禁用/无权限）。
5. 规划导航与信息架构、表单与校验。
6. 落地交给 `web.frontend-implementation`。

## 交付结果

- 系统界面的设计方向和规范（token + 组件模式 + 布局）。
- 数据展示和状态设计。
- 落地方向。

## 默认边界

- **读文件**：是。
- **写文件**：是（生成界面代码/设计）。
- **执行命令**：是（可选预览）。
- **网络**：否。
- 定系统界面方向和规范，落地交给 implementation。

## 与相邻 Skill 的区别

| Skill | 取向 |
| --- | --- |
| `web.interface-design` | **系统/产品界面**——最少惊讶、一致、高效（Ant Design/Material 那套） |
| `web.frontend-design` | **营销/创意网页**——跳出框架、视觉冲击（Awwwards 那套） |
| `web.frontend-implementation` | 落地实现（design 定方向，implementation 实现） |

## 行为案例

### 案例 1：典型成功场景

**输入**：用户说「帮我设计一个订单管理后台的 dashboard」。

**预期行为**：
1. 理清核心任务（查订单、筛选、改状态、看指标）。
2. 建 token 系统（间距 4/8/16、语义色、字号阶梯）。
3. 设计信息层级：顶部指标卡 → 筛选栏 → 订单表格（排序/分页/密度/空状态）。
4. 覆盖完备状态（加载骨架、空列表、错误、无权限）。
5. 统一 Lucide 图标、禁 emoji、克制动效。
6. 落地交给 `web.frontend-implementation`。

### 案例 2：边界场景（误用创意手法）

**输入**：用户说「给这个 admin 后台整点先锋视觉、实验性排版」。

**预期行为**：
1. 提示：系统界面的取向是「最少惊讶」，实验性排版会伤害可用性和一致性。
2. 建议把创意感克制地放在品牌层（logo、登录页、空状态插画），核心工作界面保持规范一致。
3. 若用户确实要 Awwwards 级创意站 → 路由到 `web.frontend-design`。
4. **不得**给数据密集的工作界面套实验性排版和物理动效。
