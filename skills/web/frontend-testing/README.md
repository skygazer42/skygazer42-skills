## 一句话定位

使用项目已有测试工具和真实浏览器验证前端行为，复现问题，并在授权时补充聚焦回归测试。

## 适用场景

- 验证某个 UI 流程是否真实可用。
- 复现前端 Bug，并记录稳定的复现步骤。
- 检查移动端或指定视口下的响应式行为。
- 检查键盘操作、焦点顺序、可访问名称和可见反馈。
- 检查浏览器控制台错误和失败请求。
- 为已确认回归添加最小行为测试。
- 修复后重新运行聚焦验证。

典型请求：

```text
在移动端视口验证导航后菜单是否关闭，并检查控制台和相关网络请求。
```

## 不适用场景

- 主要目标是开发功能：使用 `web.frontend-implementation`。
- 主要目标是阅读 diff 并给出 review findings：使用 `web.frontend-review`。
- 只看后端日志、任务、数据库或服务故障：使用后端测试或 `backend.backend-debugging`。
- 用户只要理论测试方案且没有工作区：普通分析即可，不应声称已经运行。

## 执行前需要的信息

- 验收标准和需要验证的用户行为。
- 支持的浏览器、设备或视口；未指定时使用仓库已有约定。
- 应用启动命令、测试命令和现有测试工具。
- 相关账号、Fixture、服务或本地配置是否可用。
- 如果要写测试，明确授权和目标回归。

## 执行流程

1. 固定验收标准、环境、命令和相关测试。
2. 优先使用仓库已安装的测试 Runner 和浏览器工具。
3. 行为依赖集成时启动真实应用，不用源码阅读替代。
4. 执行主路径和最小必要的加载、错误、空、校验、重复操作与导航路径。
5. 根据请求检查键盘、焦点、可访问名称、视口、控制台和网络请求。
6. 需要补覆盖时，写一个对回归敏感、对实现细节不敏感的最小测试。
7. 记录环境、命令、步骤、观察结果和未完成项。

## 交付结果

最终结果必须分为：

- **Passed**：实际运行且符合预期。
- **Failed**：实际运行且出现问题，附复现步骤。
- **Blocked**：尝试运行但被环境、凭据、服务或 Fixture 阻塞。
- **Not run**：未执行，不能算通过或失败。

如果修改测试，还要列出测试文件、断言目标和精确运行命令。

## 权限

| 权限 | 声明 | 用途 |
| --- | :---: | --- |
| 网络 | 是 | 本地应用、浏览器请求或明确授权的测试环境可能需要网络 |
| 读文件 | 是 | 阅读应用代码、配置和现有测试 |
| 写文件 | 是 | 用户要求时添加或修改测试 |
| 执行命令 | 是 | 启动应用、Runner 和浏览器工具 |

写权限不代表每次都修改文件。只要求验证时，默认保持产品代码和测试不变。

## 默认边界

- 视觉或交互结论必须来自真实浏览器行为。
- 有确定性等待条件时，不使用任意 sleep 或固定超时。
- 不为了让脆弱测试通过而改写生产功能。
- 不对共享或生产环境执行破坏性操作。
- 没有运行的检查不能写成通过。

## 失败时如何处理

应用无法启动或缺少凭据、服务、浏览器、Fixture 时，保留失败输出，指出最小缺失条件，并继续完成不受阻塞的静态或单元检查。结果中必须明确说明覆盖范围不足。

## 行为案例

当前案例位于 [`tests/cases.yaml`](tests/cases.yaml)：

- `reproduces-browser-failure`：在真实浏览器中复现移动导航问题，记录视口、控制台和请求证据。
- `adds-focused-regression-test`：为重复提交增加最小用户行为测试，不使用 sleep 同步。

## 与相邻 Skill 的区别

```text
Frontend Testing：       运行证据，必要时补测试
Frontend Review：        以代码审查发现风险
Frontend Implementation：实现产品行为或修复
```
