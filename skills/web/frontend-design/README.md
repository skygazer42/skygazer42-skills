# Frontend Design（前端设计）

## 一句话定位

构建新 UI 或重塑现有 UI 时，给出独特、有意图的视觉设计方向——配色、排版、布局，拒绝模板化的「AI 味」默认。

## 适用场景

- 用户说「帮我设计一个页面」「做好看点」「这个 UI 太普通了」。
- 用户想要一个有独特视觉身份、不像模板的界面。
- 需要确定审美方向、配色方案、字体搭配、布局概念。
- 用户明确拒绝了「感觉像 AI 生成」的设计。

## 不适用场景

- 用户要的是**功能实现**（连 API、状态管理、表单校验）——那是 `web.frontend-implementation`。
- 用户要审查已有前端代码——那是 `web.frontend-review`。
- 非前端/非视觉任务。

## 执行前需要的信息

- 设计 brief（产品是什么、受众、页面的核心任务）——如果没有，Skill 会先帮你定下来。
- 任何已知的品牌、偏好、参考。

## 执行流程

1. 扎根主题——定下产品、受众、页面唯一任务。
2. 第一遍：头脑风暴设计计划（Color / Type / Layout / Signature 的 token 系统）。
3. 第二遍：对照 brief 审查，砍掉任何读起来像通用默认的部分。
4. 确认独特性后才写代码，每个决策从设计计划推导。
5. 边构建边自我批评，砍掉不服务 brief 的装饰。
6. 设计落地交给 `web.frontend-implementation`。

## 交付结果

- 一个紧凑的设计 token 系统（配色 hex、字体角色、布局概念、signature 元素）。
- 从设计计划推导的 UI 代码，或明确的设计方向。
- 一个可自圆其说的审美风险。

## 默认边界

- **读文件**：是。
- **写文件**：是（生成 UI/设计代码）。
- **执行命令**：是（可选——截图预览、启动本地渲染）。
- **网络**：否。
- 定方向和视觉设计，不负责完整功能实现和数据流。

## 与相邻 Skill 的区别

| Skill | 区别 |
| --- | --- |
| `web.frontend-implementation` | design **定审美方向**；implementation **落地功能**、连 API、覆盖状态、保证正确性和无障碍 |
| `web.frontend-review` | design 做设计；review 审查已有代码 |
| `engineering.brainstorming` | brainstorming 探索**做什么**（需求）；frontend-design 探索**长什么样**（视觉） |

## 行为案例

### 案例 1：典型成功场景

**输入**：用户说「给我的咖啡烘焙工作室做一个落地页，别整得像模板」。

**预期行为**：
1. 扎根主题——精品咖啡烘焙，受众是咖啡爱好者，页面任务是让人预约品鉴。
2. 从咖啡世界提取独特元素（烘焙曲线、产地地图、风味轮）作为 signature。
3. 建 token 系统：不用赤陶+奶油的默认组合，而是从深烘焙的实际色谱推导配色。
4. 对照 brief 审查——如果配色像通用「暖奶油+衬线」默认就改掉。
5. 确认独特后写代码，落地交给 `web.frontend-implementation`。

### 案例 2：边界/失败场景（brief 指定了默认样子）

**输入**：用户说「我就要那种黑底 + 亮绿强调色的极客风」——这恰好是 AI 默认三样式之一。

**预期行为**：
1. **brief 的话优先**——用户明确指定了方向，就精确遵循，不因为它是「默认样式」而擅自改成别的。
2. 在这个方向内，仍然把 signature 元素和排版做出独特性。
3. **不得**因为「这是 AI 默认样式」就违背用户明确的要求。
