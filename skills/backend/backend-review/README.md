## 一句话定位

沿真实请求与数据路径审查后端变更，优先发现会影响安全、正确性、数据和可靠性的缺陷。

## 适用场景

- 审查 API、服务、任务、数据库或 Migration 变更。
- 审查后端 Pull Request 或本地 diff。
- 检查资源级授权、注入、密钥处理和敏感日志。
- 检查事务、约束、部分失败、回滚、重复投递和并发。
- 检查超时、取消、重试、资源清理和可观测性。
- 检查 Schema、接口兼容性和测试覆盖。

典型请求：

```text
审查账户数据导出接口，优先检查资源所有权和数据暴露问题，不要修改代码。
```

## 不适用场景

- 用户要求直接实现或修复：使用 `backend.backend-implementation`。
- 用户报告现网或本地故障并要求找根因：使用 `backend.backend-debugging`。
- 主要审查 UI、交互或浏览器行为：使用 `web.frontend-review`。
- 只想讨论代码风格、格式或命名偏好。

## 执行前需要的信息

- 变更说明、验收标准和 diff。
- 受影响入口、调用方、契约、模型、Migration、配置和测试。
- 认证、授权、数据所有权和部署约束。
- 如需运行验证，对应数据库、服务或测试环境条件。

## 执行流程

1. 阅读变更及受影响入口、调用方、数据和配置。
2. 追踪验证、授权、业务逻辑、持久化、外部调用和响应处理。
3. 检查成功、失败、部分失败、回滚、重复请求、重试、超时、取消和并发路径。
4. 检查注入、访问控制、密钥、敏感日志和信息泄露。
5. 检查 Schema 兼容性、约束、事务、Migration 安全、资源清理和运维影响。
6. 判断测试是否覆盖最高风险行为，并能对目标回归失败。
7. 只输出有证据的发现，并按严重度排序。

## 交付结果

每条 finding 应包括：

- 严重度及是否阻塞发布。
- 用户、数据、安全或运维影响。
- 文件、行号或明确受影响路径。
- 支持结论的实现、配置、Migration 或测试证据。
- 最小可行修复方式。

没有确认缺陷时应明确说明，并列出尚未验证的集成、数据库或部署风险。

## 权限

| 权限 | 声明 | 用途 |
| --- | :---: | --- |
| 网络 | 否 | 默认基于本地仓库与可用运行证据 |
| 读文件 | 是 | 阅读接口、服务、Schema、配置和测试 |
| 写文件 | 否 | 审查模式默认不实现修复 |
| 执行命令 | 是 | 运行验证性测试和静态检查 |

## 默认边界

- 未单独要求修复时不修改文件。
- 不把格式、命名或架构偏好说成正确性缺陷。
- 实现、Migration 或配置可读时，不凭假设描述运行行为。
- 发现密钥时只安全指出位置，不在输出中复制敏感内容。
- 不把未验证的部署风险写成已确认故障。

## 失败时如何处理

缺少代码、Schema、部署限制或测试输出时，列出缺失证据，并只对可验证路径下结论。需要数据库或外部环境才能确认的内容保留为残余风险。

## 行为案例

当前案例位于 [`tests/cases.yaml`](tests/cases.yaml)：

- `finds-authorization-gap`：必须追踪到资源所有权，而不是只看到“已登录”。
- `checks-transaction-boundary`：必须分析两个写操作之间的部分失败、重试和数据完整性。

## 与相邻 Skill 的区别

```text
Backend Review：        审查计划中或已经完成的变更
Backend Implementation：实现或修复后端功能
Backend Debugging：     对已经出现的故障定位根因
```
