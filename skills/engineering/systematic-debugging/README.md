# Systematic Debugging（系统性排障）

## 一句话定位

遇到 bug、测试失败或异常行为时，走四阶段根因调查流程，修复根因而非症状。

## 适用场景

- 测试失败。
- 生产环境 bug。
- 异常行为。
- 性能问题。
- 构建失败。
- 集成问题。

**尤其在这些时候使用：**
- 时间压力下（紧急情况最诱人猜）。
- "快速修一下"看起来很明显。
- 已经试了好几个修复。
- 上一个修复没奏效。
- 不完全理解问题。

## 不适用场景

- bug 的根因已经通过本流程或其他手段**确凿定位**——直接修。
- 这是纯询问（"这个错误是什么意思"）——可以直接回答。

## 执行前需要的信息

- 错误信息、日志、堆栈跟踪。
- 复现步骤（如果已知）。
- 最近变更（git log / diff）。
- 环境信息。

## 执行流程

1. Phase 1 — 根因调查：读错误、复现、检查变更、追踪数据流。
2. Phase 2 — 模式分析：找正常案例、对比差异、理解依赖。
3. Phase 3 — 假设验证：单一假设、最小测试、一次一个变量。
4. Phase 4 — 实施修复：创建测试、单一修复、验证。若 ≥3 次修复失败则质疑架构。
5. 按问题领域路由到领域 Skill（backend-debugging / frontend-testing 等）。

## 交付结果

- 根因陈述（含置信度）。
- 复现步骤或决定性证据。
- 影响范围分析。
- 最小修复建议。
- 验证计划。

## 默认边界

- **读文件**：是。
- **写文件**：否（默认不改代码，除非用户要求修复）。
- **执行命令**：是（跑测试、收集诊断数据）。
- **网络**：否。
- 不把重启、加重试、增大超时当根因。

## 与相邻 Skill 的区别

| Skill | 区别 |
| --- | --- |
| `backend.backend-debugging` | systematic-debugging 是**通用方法论**；backend-debugging 是**后端领域诊断**（API/数据库/队列/缓存） |
| `web.frontend-testing` | systematic-debugging 找根因；frontend-testing 用浏览器验证行为 |
| `engineering.tdd` | TDD 是**开发方法**（先写测试）；systematic-debugging 是**诊断方法**（先找根因） |

## 行为案例

### 案例 1：典型成功场景

**输入**：「API /users 返回 500，之前好的」。

**预期行为**：
1. Phase 1：读错误日志、检查最近提交、尝试复现。
2. Phase 2：找正常工作的类似 endpoint 对比。
3. Phase 3：形成假设——"新加的 validation 没处理 null 输入"。
4. Phase 4：创建复现测试，修根因，验证。
5. 若领域问题涉及数据库/缓存/队列 → 路由到 `backend.backend-debugging`。

### 案例 2：边界/失败场景

**输入**：开发者说「我试了 4 种修复方法了，每次修好一个地方另一个地方又坏了」。

**预期行为**：
1. 这是 ≥3 次修复失败的信号。
2. **停**——不再试第 5 次。
3. 质疑架构：这个 pattern 根本上是正确的吗？是不是"靠惯性硬撑"？
4. 与用户讨论是否需要架构级重构。
5. **不得**继续尝试第 5 种修复。
