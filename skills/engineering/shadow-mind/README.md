# shadow-mind · 并行认知核心（Shadow Mind）

## 一句话定位

让实现与审阅发生在同一轮工作中：主 Agent 持续推进主线任务，多个**持久、独立**的认知核心（架构审阅 / 项目事实核验 / 文档维护 / 完成度审阅）并行工作，各自认领一项稳定职责，独立决定何时检查、行动或汇报，并在错误变得昂贵之前介入。

## 适用场景

- 主 Agent 正在实现一个**中等以上复杂度**的变更（涉及多模块、接口、状态），希望实现过程中就有人独立盯着架构、事实、文档和完成度。
- 在**实现中途**和**声称完成之前**两个时刻，需要独立于主 Agent 的核验视角。
- 希望文档随实现同步更新，而不是事后补。
- 需要防止主 Agent 编造项目事实、遗漏约束、走错路线。

## 不适用场景

- **没有持续的主线工作**（纯问答、单次查询）——没有「并行」可言。
- 纯文案 / 文档小改——用轻量检查即可。
- **发布前自动化外审门禁**（打包 diff + 密钥扫描 + 外部引擎）→ `engineering.autoreview`。
- 一次性的主 Agent 主导代码审查对话 → `engineering.code-review`。
- 主 Agent 自己先验证再声称完成 → `engineering.verification-before-completion`（完成度审阅核心是独立旁证，不替代）。

## 执行前需要的信息

- **启用的认知核心**：默认 4 个（`references/`），可增删自定义——新视角 = 新 Markdown 定义，遵循 SKILL.md 的认知核心铁律。
- **部署方式**：并行子代理（首选，参考 `engineering.subagent-driven-development` 的派发机制）或检查点佩戴（无子代理时串行跑各核心 pass）。
- **工作轨迹**：核心接收净化后的文本轨迹（用户消息 + 主 Agent 普通文本 + 工具调用及结果概述），不含主 Agent 思考与完整工具输出。
- **明确的职责范围**：特别是写权限——只有文档维护核心被授予 `write`，且只写它负责的文档。

## 执行流程

1. **确定核心集**：按任务选 2–4 个核心（架构审阅 / 事实核验 / 文档维护 / 完成度审阅），或按需写新核心。
2. **选择部署方式**：环境支持子代理 → 并行派发（贴近上游）；否则检查点串行。
3. **提供净化轨迹**：把当前工作的净化文本轨迹 + 各核心定义交给核心。
4. **核心独立运行**：每个核心按职责判断是否相关；相关则用自己分配的工具做有界核验，产出报告。
5. **收口报告**：`[核心名] 差异 + 证据 + 最有效下一步`，或无发现时固定 `check: OK`；主 Agent 采纳前逐条核验。
6. **文档核心写文档**（若启用）：随实现同步维护 `docs/`、README、架构说明。
7. **完成度审阅**（若启用）：主 Agent 声称完成前，独立检查是否真满足任务要求。
8. **作废迟到结果**：用户开启新任务后，旧核心的迟到报告不投递。

## 交付结果

- **各核心的报告**：一条可行动的发现（带证据）或固定 `check: OK`；无空报告。
- **文档维护核心的文件改动**（仅当启用）：与实现变化同步的文档更新。
- **主 Agent 的核验结论**：采纳/拒绝每条发现及理由。

## 默认边界

- **网络**：否。认知核心做本地只读（或文档写）检查，不访问外部服务。
- **读文件**：是。核心用 read/grep/Glob/ls 核验仓库事实与轨迹断言。
- **写文件**：是（仅限被授予写权限的核心，当前只有文档维护核心，且只写文档，不碰代码/测试）。
- **执行命令**：否。核心不执行 shell；需要跑验证时由主 Agent 或相应验证 Skill 完成。
- **外部状态**：不 push、不改远端、不写全局配置。核心用完即弃，不跨会话残留。

## 与相邻 Skill 的区别

| Skill | 与 shadow-mind 的关系 |
| --- | --- |
| `engineering.code-review` | code-review 是主 Agent 与用户协作的一次性审查对话；shadow-mind 是**持续、并行、独立介入**的认知核心，不叫来审查而是自己决定介入 |
| `engineering.autoreview` | autoreview 是发布前的自动化外审门禁（diff + 密钥扫描 + 外部引擎）；shadow-mind 是常驻并行认知核心（架构/事实/文档/完成度） |
| `engineering.verification-before-completion` | 那是主 Agent 自己跑验证的铁律；shadow-mind 的完成度审阅核心是**独立旁证**，不替代它 |
| `engineering.systematic-debugging` | 那是排障方法论；shadow-mind 的事实核验核心在实现过程中防编造，方向不同 |
| `engineering.subagent-driven-development` | 那是子代理派发/收口的机制；shadow-mind 规定认知核心的**契约**，可用其机制部署核心 |

## 行为案例

### 案例 1：典型——多模块实现中途部署并行核心

用户实现一个权限系统，要求「边做边有人盯着」。部署架构审阅 + 项目事实核验 + 文档维护三个核心：
- 架构审阅核心发现主 Agent 把角色判断堆进 `UserService` 的 if/else，报告「职责错位：角色策略应拆出独立模块（证据：UserService 第 80–140 行）」，主 Agent 核验后重构；
- 事实核验核心发现主 Agent 声称「项目已有 UserRole」，用 grep 全仓核验后报告「无此符号」；主 Agent 修正说法；
- 文档维护核心随实现把 `docs/architecture.md` 的角色模型章节同步更新；
- 整个过程主 Agent 持续推进主线，不被打断；三条报告都有证据、都可行动。

### 案例 2：边界——完成度审阅不是「测试通过」的证明

主 Agent 声称「完成」，完成度审阅核心报告 `completion check: OK`。这不等于测试通过或已验证——核心的 OK 只代表「从净化轨迹与仓库看，没发现未满足任务要求的证据」。跑验证证明「完成」是 `verification-before-completion` 的职责；两者可同时成立但互不替代。

### 案例 3：失败——迟到结果作废

一个核心在用户已开启新任务后才完成审查。按 epoch 纪律，该迟到结果作废、不投递；核心实例用完即弃，不把旧任务的结论带进新任务。
