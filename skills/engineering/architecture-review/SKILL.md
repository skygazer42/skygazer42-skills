# 架构审查

找出架构摩擦，提出**深化机会**——把浅模块变深模块的重构。目标是可测性和 AI 可导航性。这不是代码级审查（那是 `engineering.code-review`），而是模块和接口层面的设计审查。

## 深模块词汇

用这套词，别换成"组件""服务""API""边界"——一致的语言是关键。

| 术语 | 含义 |
| --- | --- |
| **模块（Module）** | 任何有接口和实现的东西——函数、类、包、跨层切片。尺度无关。 |
| **接口（Interface）** | 调用方为了正确使用必须知道的一切：类型签名，还有不变量、顺序约束、错误模式、必需配置、性能特征。 |
| **深度（Depth）** | 接口处的杠杆——调用方每学一单位接口，能驱动多少行为。**深模块**=小接口 + 大量行为；**浅模块**=接口几乎和实现一样复杂。 |
| **接缝（Seam）** | 能改变行为而不用在该处改代码的位置；模块接口所在的地方。放在哪是独立的设计决策。 |
| **杠杆（Leverage）** | 调用方从深度获得的：每学一单位接口得到更多能力。一个实现回报 N 个调用点 + M 个测试。 |
| **局部性（Locality）** | 维护者从深度获得的：改动、bug、知识、验证集中在一处，而非散落到调用方。改一次，处处改好。 |

**深模块 = 小接口 + 大实现（追求）：**
```
┌─────────────────┐
│   小接口         │  ← 少数方法，简单参数
├─────────────────┤
│   深实现         │  ← 复杂逻辑藏在里面
│                 │
└─────────────────┘
```

**浅模块 = 大接口 + 薄实现（避免）：**
```
┌───────────────────────────┐
│   大接口                   │  ← 很多方法，复杂参数
├───────────────────────────┤
│   薄实现（只是透传）        │
└───────────────────────────┘
```

## 流程

### 1. 划定范围再扫描（YAGNI）

深化一个模块的回报是让它未来的改动更容易——所以把注意力放在**最近常改**的部分。扫描前先决定去哪看：

- 用户指定了方向（某模块、某子系统、某痛点）→ 直接用，跳过下面的推断。
- 否则走一段提交历史（`git log --oneline`）找**热点**——反复出现的文件和区域，让那些路径先吸引注意。改动分散没有明显热点 → 扩大范围。

然后探索代码库，别套僵硬的启发式——有机地探索，记下你**感到摩擦**的地方：

- 理解一个概念要在很多小模块间来回跳？
- 哪里的模块**浅**——接口几乎和实现一样复杂？
- 哪里的纯函数只是为了可测性抽出来，但真正的 bug 藏在它们**怎么被调用**里（没有局部性）？
- 紧耦合的模块从接缝处泄漏？
- 哪些部分没测试，或通过当前接口很难测？

### 2. Deletion Test

对任何你怀疑是浅的东西，做删除测试：**删掉它，会让复杂度集中，还是只是把复杂度挪个地方？**

- "集中" → 这就是你要的信号，它是个真实的浅模块，值得深化。
- "只是挪走" → 它没那么浅，放过它。

### 3. 呈现候选

把发现的深化机会列成候选清单给用户。每个候选包含：

- **涉及文件**——哪些文件/模块。
- **问题**——当前架构为什么造成摩擦（用深模块词汇）。
- **方案**——朴素英文描述会改成什么。
- **收益**——用局部性和杠杆解释，以及测试会怎么改善。
- **前后对比**——当前的浅 vs 深化后的样子。
- **推荐强度**——`强烈` / `值得探索` / `推测性`。

可视化是加分项（前后对比图很有用），但**不强制**特定工具或格式——朴素的 ASCII 图或文字描述都行。别为了做图而引入重型依赖。

呈现后**先不要提议具体接口**。问用户："这些里面你想深入哪一个？"

### 4. 拷问选定候选

用户选了一个后，用 `engineering.grilling` 和他们一起走决策树——约束、依赖、深化后模块的形状、接缝后面放什么、哪些测试能活下来。

拷问达成共识后，如果要落地，路由到对应的领域实现 Skill（`backend.backend-implementation` / `web.frontend-implementation`）。

## 与相邻 Skill 的区别

| Skill | 层面 |
| --- | --- |
| `engineering.architecture-review` | **架构/模块**层——深浅、接口、接缝、可测性 |
| `engineering.code-review` | **代码/PR**层——正确性、质量、SOLID |
| `backend.backend-review` | **后端领域**——安全、并发、数据完整性 |
| `web.frontend-review` | **前端领域**——无障碍、响应式、性能 |

## 边界

- **不直接改代码。** 审查产出候选和方向，落地交给实现 Skill。
- **不重型化呈现。** 可视化可选，不强制 HTML/CDN/图表库。
- **不越过 deletion test。** 只深化真正会集中复杂度的浅模块。
