# Architecture Review（架构审查）

## 一句话定位

扫描代码库找「深化机会」——把浅模块（大接口薄实现）变成深模块（小接口大实现），提升可测性和可导航性。架构/模块层审查，区别于代码级审查。

## 适用场景

- 用户想改进代码架构、模块设计。
- 理解一个概念要在很多小模块间来回跳（导航困难）。
- 代码难以测试，或纯函数抽出来了但 bug 藏在调用方式里。
- 想审查架构质量，而非单个 PR 的正确性。

## 不适用场景

- 审查单个 PR/diff 的正确性和质量——用 `engineering.code-review`。
- 后端安全/并发/数据审查——用 `backend.backend-review`。
- 前端无障碍/性能审查——用 `web.frontend-review`。

## 执行前需要的信息

- 代码库访问（Skill 会自己走 git 历史和探索）。
- 可选：用户指定的方向（某模块、子系统、痛点）。

## 执行流程

1. 划定范围——从 git 热点或用户指定方向出发（YAGNI）。
2. 探索代码库，记下感到摩擦的地方（浅模块、无局部性、泄漏接缝、难测）。
3. Deletion test——删掉它会集中复杂度还是只是挪走？
4. 呈现深化机会候选（涉及文件、问题、方案、收益、前后对比、推荐强度）。
5. 用户选一个 → 用 `engineering.grilling` 审问它 → 落地交给实现 Skill。

## 交付结果

- 一份深化机会候选清单（用深模块词汇）。
- 每个候选的前后对比和推荐强度。
- 选定候选经拷问后的实现方向。

## 默认边界

- **读文件**：是。
- **写文件**：否（审查不直接改代码）。
- **执行命令**：是（`git log` 找热点）。
- **网络**：否。
- 可视化可选，不强制重型报告工具。

## 与相邻 Skill 的区别

| Skill | 层面 |
| --- | --- |
| `engineering.architecture-review` | 架构/模块层——深浅、接缝、可测性 |
| `engineering.code-review` | 代码/PR 层——正确性、质量、SOLID |
| `engineering.grilling` | architecture-review 用 grilling 审问选定候选 |

## 行为案例

### 案例 1：典型成功场景

**输入**：用户说「我们的订单模块越来越难改了，帮我看看架构」。

**预期行为**：
1. 走 git 历史找订单相关的热点文件。
2. 探索，发现"理解一个订单要跳 8 个小文件"（无局部性）。
3. Deletion test：删掉那些薄薄的 handler，复杂度会集中到一个深的订单模块——信号成立。
4. 呈现候选：把 8 个浅 handler 深化为一个小接口的订单模块，附前后对比和收益（测试从 8 处集中到 1 处）。
5. 用户选定后用 `engineering.grilling` 审问接缝和测试。

### 案例 2：边界场景（deletion test 不通过 / 强推重型报告）

**预期行为**：
1. 对一个"看起来浅"但删掉只会把复杂度挪到别处的模块——**放过它**，不列为候选。
2. **不得**为了做前后对比图强行引入 Tailwind/Mermaid CDN 等重型依赖——ASCII 或文字描述即可。
3. **不得**直接改代码——产出候选和方向，落地交给实现 Skill。
