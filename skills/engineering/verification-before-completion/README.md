# Verification Before Completion（声称完成前先验证）

## 一句话定位

在任何"完成/修好/通过"的声称之前，必须先跑验证命令并拿到新鲜证据。没有证据就没有断言。

## 适用场景

- 即将声称"测试通过了"。
- 即将声称"bug 已修复"。
- 即将声称"功能完成"。
- 即将提交、创建 PR、标记 task 完成。
- 即将对任何成功/正确性状态做正面陈述。

**几乎任何声称完成/成功的场合都适用。**

## 不适用场景

- 中间步骤的进度汇报（"正在做第三步"——这不算声称完成）。
- 纯信息查询或澄清问题。

## 执行前需要的信息

- 要验证的声称（测试通过？构建成功？bug 已修？）。
- 项目对应的验证命令。

## 执行流程

1. 识别哪个命令能证明这个声称。
2. 跑完整命令（新鲜，不是缓存的结果）。
3. 读完整输出，检查退出码，数失败数。
4. 输出确认了声称？若否，如实汇报实际状态。若是，带证据给出声称。
5. 只有做完以上，才能声称。

## 交付结果

- 验证命令的输出证据。
- 明确的通过/失败/阻塞/未运行状态。

## 默认边界

- **读文件**：是。
- **写文件**：否。
- **执行命令**：是（跑测试/lint/build/校验）。
- **网络**：否。
- 不编造验证结果。不把"应该能过"当证据。

## 与相邻 Skill 的区别

| Skill | 区别 |
| --- | --- |
| `engineering.test-driven-development` | TDD 是**开发方法**（写测试驱动实现）；verification 是**完成把关**（声称前跑验证） |
| `web.frontend-testing` | frontend-testing 是**领域测试**（浏览器、UI 流程）；verification 是**纪律**（任何完成声称前） |
| `engineering.writing-plans` | writing-plans 管**计划**；verification 管计划执行后的**验收** |

## 行为案例

### 案例 1：典型成功场景

**输入**：开发者说"测试全过了，这个功能完成了"。

**预期行为**：
1. 不给通过——这是未经验证的声称。
2. 要求先跑测试命令。
3. 若跑完确实 0 失败 → "测试全部通过（34/34 PASS），功能完成"。**带到证据。**

### 案例 2：边界/违规场景

**输入**：开发者说"上次跑过了，应该还能过"。

**预期行为**：
1. 识别这是 Red Flag（"应该"）。
2. 拒绝接受缓存的旧结果。
3. 要求重新跑验证。
4. **不得**因为"上次通过了"就接受声称。
