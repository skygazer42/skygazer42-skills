# Brainstorming（头脑风暴）

## 一句话定位

在任何创意或实现工作之前，通过结构化对话把模糊需求变成经批准的设计方案。

## 适用场景

- 用户提出一个新功能、组件或页面，但没有明确的设计方案。
- 用户说「我想做一个 X」但需求还模糊。
- 需要先厘清做什么、为什么做、怎么做，再开始写代码。
- 跨多个子系统的复杂需求需要先拆解再逐个设计。

## 不适用场景

- 用户已经给了**非常精确、一步到位**的实现指令（如「把第 5 行的 `color: red` 改成 `color: blue`」）。这类直接执行即可，不需要走完整设计流程。
- 用户只是问一个事实性问题（如「这个文件是干什么的」）。
- 纯代码审查、测试或排障任务——这些有各自的 Skill，但若这些任务涉及「先厘清目标再动手」，brainstorming 仍然适用。

## 执行前需要的信息

- 用户的需求描述（哪怕一句话）。
- 当前项目的上下文（文件、文档、最近提交——Skill 自己会读取）。
- 任何用户主动提供的约束（技术栈、时间、性能要求等）。

## 执行流程

1. 探索项目上下文（读文件、文档、最近提交）。
2. 一次一个问题地澄清意图、约束和成功标准。
3. 提出 2-3 个方案，给出权衡和推荐。
4. 逐节展示设计，每节获用户批准。
5. 写设计文档（`docs/specs/`）。
6. 规格自审（占位符、矛盾、歧义、范围）。
7. 用户审阅规格并批准。
8. 过渡到 `engineering.writing-plans` 创建实现计划；**不直接调用实现类 Skill**。

## 交付结果

- 已批准的设计文档（`docs/specs/YYYY-MM-DD-<topic>-design.md`）。
- 明确的实现方向（路由到哪个领域 Skill，需要哪些资源）。

## 默认边界

- **读文件**：是（探索项目上下文）。
- **写文件**：是（写设计文档）。
- **执行命令**：否（设计阶段不运行代码）。
- **网络**：否。
- **写代码 / 修改生产文件**：否——这是本 Skill 的核心边界。任何实现动作必须在设计审批之后，由 `engineering.writing-plans` 和对应的领域 Skill 执行。

## 与相邻 Skill 的区别

| Skill | 区别 |
| --- | --- |
| `engineering.writing-plans` | brainstorming 产出**设计方案**（做什么），writing-plans 把方案拆成**实现计划**（怎么做） |
| `web.frontend-implementation` | brainstorming 只设计不实现；实现是领域 Skill 的事 |
| `backend.backend-implementation` | 同上 |
| `backend.backend-debugging` | debugging 是「找出为什么坏了」并定位根因；brainstorming 是「想清楚要做什么」 |

brainstorming 是管「设计」的，不跨越到「写代码」或「修 bug」。

## 行为案例

### 案例 1：典型成功场景（新功能）

**输入**：用户说「我想给我的博客加一个搜索功能」。

**预期行为**：
1. Skill 探索当前博客项目的结构。
2. 一次一个问题地澄清：全文搜索还是标题搜索？要不要高亮？前端还是后端实现？有没有现成的搜索库？
3. 提出 2-3 个方案（客户端搜索 vs 服务端搜索 vs 第三方服务），给出权衡。
4. 用户选方案后，逐节展示架构/组件/数据流/错误处理设计，逐节获批准。
5. 写设计文档并提交。
6. 规格自审 + 用户审阅。
7. 调用 `engineering.writing-plans`。
8. **绝不**自行写搜索代码或修改项目文件。

### 案例 2：边界/失败场景（用户给了明确指令）

**输入**：用户说「把 `Button.css` 第 12 行的 `font-size: 14px` 改成 `16px`」。

**预期行为**：
1. 这是精确、一步到位的指令，不需要设计流程。
2. Skill 应识别这是 trivial change，给出极简短的设计确认（如「收到，把 Button.css 的 font-size 从 14px 改成 16px。你要我做这个修改吗？还是还有别的需要一起考虑？」），而不是走完整的 8 步检查表。
3. **不得**编造额外的设计步骤或要求用户澄清不必要的东西。
