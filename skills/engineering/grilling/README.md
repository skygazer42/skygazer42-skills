# Grilling（灵魂拷问）

## 一句话定位

无情审问一个计划、设计或决策，一次一个问题走决策树，在动手前把藏着的漏洞和未定的决策逼出来。

## 适用场景

- 用户有了方案/设计，想在写代码前压力测试。
- 计划看起来"差不多了"，但可能有没想清的地方。
- 重大不可逆决策之前（技术选型、数据模型、API 契约）。
- 用户明确要求被 grill / 拷问 / 挑战思路。

## 不适用场景

- 还没有方案、需要从零探索——用 `engineering.brainstorming`。
- 方案已经过拷问、要拆成计划——用 `engineering.writing-plans`。
- 纯事实查询——直接查，不需要拷问。

## 执行前需要的信息

- 一个待拷问的方案、设计或决策（用户提供）。
- 对相关代码库/环境的访问（Skill 会自己查事实）。

## 执行流程

1. 走决策树的每个分支，识别决策之间的依赖。
2. 一次一个问题——每个给出推荐答案和理由。
3. 能查的事实自己查（文件、代码、工具），只把决策留给用户。
4. 等用户回答每个问题后再问下一个。
5. 达成共识后才结束——不在共识前行动。

## 交付结果

- 一个被压力测试过的、清晰的共同理解。
- 暴露出的漏洞、风险、未定决策清单。
- 路由建议（经受住 → writing-plans；有根本问题 → brainstorming）。

## 默认边界

- **读文件**：是（查事实）。
- **写文件**：否。
- **执行命令**：否。
- **网络**：否。
- 不实现、不写代码——达成共识前不行动。

## 与相邻 Skill 的区别

| Skill | 区别 |
| --- | --- |
| `engineering.brainstorming` | brainstorming **建设性**探索（帮方案结晶）；grilling **批判性**攻击（逼出漏洞） |
| `engineering.writing-plans` | grilling 拷问方案；writing-plans 拆解经受住拷问的方案 |
| `engineering.architecture-review` | architecture-review 用 grilling 来审问选定的架构改进候选 |

## 行为案例

### 案例 1：典型成功场景

**输入**：用户说「我打算给订单系统加一个异步队列处理支付回调，帮我 grill 一下这个方案」。

**预期行为**：
1. 先查事实（现有支付流程、有没有队列基础设施）——不问用户。
2. 一次一个问题走决策树：回调幂等性怎么保证？（给推荐）→ 等答 → 队列失败重试策略？（给推荐）→ 等答 → 回调顺序有没有依赖？（给推荐）→ 等答……
3. 逼出没想清的地方（如"回调乱序到达怎么办"）。
4. 达成共识后路由到 `writing-plans`。

### 案例 2：边界场景（一次问一堆 / 问事实）

**预期行为**：
1. **不得**一次抛出 5 个问题——一次一个，等回答。
2. **不得**问"你们用什么数据库"这种能自己 grep 的事实。
3. 达成共识前**不得**开始写实现代码。
