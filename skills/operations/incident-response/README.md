# 事故响应（Incident Response）

## 一句话定位

管理生产事故从检测到复盘的全生命周期——triage 严重级别、识别影响、沟通与状态更新草稿、缓解与恢复验证、无责备复盘。**外部通知只生成草稿**，重启/回滚/部署/paging/发消息等操作需分别获得明确授权；**证据不足时标注「未知」**，不编造影响人数、根因、恢复时间或责任人。

## 适用场景

- 生产服务宕机、告警需要评估严重级别
- 事故进行中的状态更新请求（向团队/客户说明情况）
- 缓解动作后的恢复验证
- 事故解决后写无责备复盘（5 Whys、时间线、行动项）

## 不适用场景

- 定位代码层面的根因与修复建议 → `backend.backend-debugging`
- 日常运维变更、部署排期 → 本 Skill 只管事故
- 自动发送对外通知、自动 paging、自动写状态页 → 本 Skill 只生成草稿，动作需独立授权

## 执行前需要的信息

- 事故描述或告警内容（越具体越好：症状、时间、影响范围、已知证据）
- 可选：当前阶段（triage / update / postmortem）
- 可选：已有证据（日志、监控截图、错误信息）
- 无信息时：先问当前处于事故哪个阶段，不编造

## 执行流程

1. **Triage**：评估 SEV1-4（基于证据），识别受影响系统和用户，分配角色（IC/沟通/响应者）
2. **Communicate**：起草内部状态更新（如需客户沟通也起草），约定更新节奏
3. **Mitigate**：记录缓解动作 + 每条的证据，跟踪时间线，用可验证判据确认恢复
4. **Postmortem**：重建时间线，5 Whys 根因分析，无责备，带负责人行动项

## 交付结果

- **状态更新草稿**：严重级别/状态/影响/当前状态/已采取行动/下一步/时间线
- **复盘文档草稿**：摘要/影响/时间线/根因/5 Whys/做得好与不好/行动项/经验教训
- **取证建议**：证据不足时明确「未知」+ 下一步查什么

## 默认边界

- **读文件**：是（日志、证据、runbook）
- **写文件**：否（复盘文档以草稿形式交付，由用户落盘）
- **执行命令**：是（只读诊断命令，如日志查询）
- **网络**：否
- **事实边界不可越**：不编造影响/根因/恢复时间/责任人；不自动发任何外部通知；每类破坏性/对外操作都需独立授权

## 与相邻 Skill 的区别

| Skill | 区别 |
| --- | --- |
| `backend.backend-debugging` | 定位代码根因、影响范围、修复建议（不改代码）；本 Skill 管理整个生产事故生命周期，含严重级别/沟通/复盘 |
| `engineering.systematic-debugging` | 四阶段根因调查方法论；本 Skill 是事故流程编排，可调用其调查思路 |
| `marketing.seo` 等 | 无重叠 |

## 行为案例

### 案例 1：SEV1 事故全流程

**输入**：「我们出事故了，支付服务 503s」。

**预期行为**：
1. 先确认阶段（triage）
2. 评估严重级别（服务不可用 → SEV1，标注「待确认影响范围」）
3. 起草状态更新：当前状态/已采取行动/下一步/时间线
4. 列出缓解动作建议 + 所需授权
5. 提醒外部通知只生成草稿

### 案例 2：证据不足不编造

**输入**：「支付服务有点慢，可能影响了很多人」。

**预期行为**：
1. 明确标注影响人数「未知」，不根据「可能」猜测
2. 定级保守（信息不足时按 SEV2 处理并标注）
3. 列出取证动作：查错误率指标、看 SLI、确认受影响节点
4. 状态更新只写已确认事实，待确认项单列

### 案例 3：恢复验证

**输入**：「感觉恢复了，帮我发个恢复公告」。

**预期行为**：
1. 不直接发布——先要求可验证判据（错误率连续归零的时长、重放结果）
2. 证据不足则状态仍标「监控中」，不下「已恢复」结论
3. 对外公告只生成草稿，由用户审阅后自行发送
