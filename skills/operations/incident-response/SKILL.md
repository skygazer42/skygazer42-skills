# 事故响应（Incident Response）

管理一个生产事故从检测到复盘的完整过程。先弄清当前处于哪个阶段，再按对应模式推进。

## 模式

```
new [description]      # 开始一个新事故：triage 严重级别、识别受影响系统、分配角色
update [status]        # 发布状态更新：事实性更新、行动、下一步与 ETA
postmortem             # 用事故数据生成复盘文档
```

未指定模式时，先问当前处于事故的哪个阶段。

## 流程

```
┌─────────────────────────────────────────────────┐
│                 INCIDENT RESPONSE                 │
├─────────────────────────────────────────────────┤
│  阶段 1：TRIAGE                                   │
│  ✓ 评估严重级别（SEV1-4）                        │
│  ✓ 识别受影响的系统和用户                        │
│  ✓ 分配角色（IC、沟通、响应者）                  │
│                                                   │
│  阶段 2：COMMUNICATE                              │
│  ✓ 起草内部状态更新                              │
│  ✓ 起草客户沟通（如需）                          │
│  ✓ 约定战情室与更新节奏                          │
│                                                   │
│  阶段 3：MITIGATE                                 │
│  ✓ 记录已采取的缓解步骤                          │
│  ✓ 跟踪事件时间线                                │
│  ✓ 确认恢复（验证，不只凭感觉）                  │
│                                                   │
│  阶段 4：POSTMORTEM                               │
│  ✓ 无责备复盘文档                                │
│  ✓ 时间线重建                                    │
│  ✓ 根因分析（5 Whys）                            │
│  ✓ 带负责人的行动项                              │
└─────────────────────────────────────────────────┘
```

## 严重级别分类

| 级别 | 标准 | 响应时间 |
| --- | --- | --- |
| SEV1 | 服务不可用，全部用户受影响 | 立即，全员投入 |
| SEV2 | 主要功能降级，大量用户受影响 | 15 分钟内 |
| SEV3 | 次要功能问题，部分用户受影响 | 1 小时内 |
| SEV4 | 外观或低影响问题 | 下一个工作日 |

> 严重级别的判断只能基于**实际证据**。只有模糊描述时，标注为「信息不足，建议升级按 SEV2 保守处理」，并把需要补的信息列为下一步取证动作，不得凭空定级或编造影响人数。

## 沟通指导

按固定节奏提供清晰、事实性的更新，包含：正在发生什么、谁受影响、我们在做什么、下次更新的时间。

**只写事实**：已确认的、证据支持的。不确定的内容标「待确认」，不推测、不渲染恐慌。

## 缓解与恢复验证

记录缓解动作时，逐条说明**证据**（日志/监控/指标/复现消失），恢复状态必须有可验证的判据（如「错误率连续 N 分钟归零」「重放成功」），不能只凭「看起来好了」就宣布恢复。

## 外部通知边界（只生成草稿）

任何**对外通知**（客户沟通、状态页更新、聊天频道广播、on-call 呼叫）都只**生成草稿**交给用户，绝不自动发送。每类操作——重启、回滚、部署、paging、对外发消息——都需要**分别独立获得用户明确授权**后才执行，缺一项授权就只交付建议，不动作。

| 操作 | 默认行为 |
| --- | --- |
| 起草状态更新/客户沟通 | 生成草稿，用户审阅 |
| 重启服务/回滚/部署 | 只有明确授权后执行，否则只给命令与风险评估 |
| on-call paging / 拉人 | 只有明确授权后执行，否则只给名单与话术 |
| 创建频道/发送消息/写状态页 | 只生成草稿，不发送 |

## Tips

1. **立即开始记录** —— 不要等信息完整。边学边更新。
2. **更新保持事实性** —— 我们知道什么、做了什么、下一步是什么。不推测。
3. **复盘无责备** —— 关注系统和流程，不针对个人。
4. **证据不足标「未知」** —— 影响人数、根因、恢复时间、责任人在证据不足时一律标「未知」，并列出下一步取证动作（查哪个日志、看哪个指标、问谁）。

## 任务完成自检

- [ ] 严重级别是否基于实际证据而非猜测？
- [ ] 影响、根因、恢复时间、负责人是否都有证据支撑？没有的是否标「未知」？
- [ ] 恢复是否已用可验证判据确认，而非「看起来好了」？
- [ ] 外部通知是否只生成了草稿、未自动发送？
- [ ] 重启/回滚/部署/paging/发消息是否都分别获得过明确授权？
- [ ] 复盘是否无责备、含 5 Whys 与带负责人的行动项？
